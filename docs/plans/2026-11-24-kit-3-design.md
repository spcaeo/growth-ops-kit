## 2. The idea

One **central local database** per project (SQLite, one file, in the project folder) holds the state every agent
shares: tasks and steps, the journal, the verdicts, and a new **work board**: every page, the stage it is at, and a
queue of **jobs**. Agents and a machine runner **pull** the next job they can do. Slow shared doors (Google, the
browser pool, the owner's preview, shared code) are **resources** the database hands out one turn at a time.

The kit is divided into **micro kits**, one per group of the activity map. Each micro kit owns its tools, its jobs
and its tables, and talks to the others only through the database.

```
                    ┌──────────────── growth.db (project folder) ────────────────┐
                    │ tasks · steps · journal · verdicts · pages · jobs · leases  │
                    │ resources (google pacer, browsers, ports, shared-code lock) │
                    │ events (every change, who, when: real timings)              │
                    └───────▲─────────▲──────────▲──────────▲─────────▲──────────┘
                            │ pull    │ pull     │ pull     │ pull    │ owner
   research agent (paced) ──┘         │          │          │         └── owner answers, the yes
   planner + plan reviewer ───────────┘          │          │
   builders, each in its own lane (worktree + port) ─────────┘
   machine runner: build · link graph · gate · shots · click-test · READY, side by side, load-guarded
```

## 4. The store

- **File:** `<project>/state/growth.db`, SQLite in WAL mode, `busy_timeout` 10 s, every write in `BEGIN IMMEDIATE`.
  Python's own `sqlite3`: no new add-on. Module `kit/tools/store.py`.
- **Mirrors keep the files.** After each write the store rewrites the readable mirror (`docs/tasks.json`,
  `journal/entries.jsonl`, `journal/ready.json`, `journal/ready-failed.json`, `journal/preflight.json`) atomically, so
  the hooks, the permissions, the owner journal page, git diffs and old readers keep working, and a project still moves
  between machines as plain files. The mirror carries no lock file any more.
- **The files can win.** The store records each mirror's hash when it writes it. If a mirror is changed outside the store
  (restored from git, copied from another machine), the next open imports it and logs an event. A missing database is
  rebuilt from the mirrors.
- **One access layer.** Every module reads tasks, journal entries and verdicts through the store
  (`store.tasks_doc()`, `store.journal_entries()`, `store.verdicts(kind)`), never by opening the file. A test fails when
  a module opens one of the mirrored files directly.
- **Each micro kit owns its tables** and registers them with `store.ensure(name, schema, version)`.
- Not moved in this release: the signed approvals log (its trust comes from the owner's key), the steps log
  (written by people), research records and Markdown files (one per page, no contention).

## 5. The board and jobs

- **Pages:** path, key, type, cluster, stage, holder, updated. Stages follow the activity map line: research, plan,
  plan-review, preflight, build, cleanup, evidence, ready, review, owner, release, measure.
- **Jobs:** id, kind, page, micro kit, how it runs, needs (job ids), resource, status (queued, claimed, done, failed,
  blocked), holder, lease until, attempts, proof, times. A job is claimable when all its needs are done and its
  resource is free.
- **The pipeline is data:** `kits.json` lists, per page type, the job kinds in order and what each needs, so adding a
  step is a manifest change, not code.
- **Pull, not push:** `growth work next --kit <k> --agent <name>` claims one job with a lease (30 min default),
  `growth work beat <id>` renews it, `growth work done <id> --proof "..."` finishes it (the proof check is the one
  `growth tasks` already uses) and creates the next jobs, `growth work fail <id> --why "..."`. A lease that runs out puts
  the job back in the queue, so a stopped agent never blocks a page.
- **Ticks from jobs:** finishing a job ticks the matching task step with its proof and time, so the task list stays
  true without bulk ticking.
- **`growth board`** shows every page, its stage, who holds it and what it waits for; `growth board times` prints wait
  and work time per stage from the events.

## 6. Resources

| Resource | Kind | Rule |
| --- | --- | --- |
| google | pacer | one turn every 20 to 30 s (random), for all agents; `growth pace google` blocks until the turn; `--robot` pauses everyone 10 min (OWNER-RULES "Slow Google searches", now code) |
| browser | pool | as many as the machine allows (default 3; lower when free memory is under 20 % or load is high) |
| port | pool | lane preview ports 18440 to 18459 |
| owner-preview | lock | the one preview address; only the READY run and its move use it |
| shared-code | lock | one writer; on release the fingerprints of every READY page are compared and only pages whose built output changed get a re-check job |

## 7. Lanes and the machine runner

- `growth lane open <path> --agent <name>`: a worktree from the integration branch, a port from the pool, the clone's
  `node_modules` linked, its own `growth serve` of its own build. The builder checks on its own port; READY stays on the
  owner's one address (owner, 17 Nov 2026: "it should be on the same one"). `growth lane close` stops the server, removes
  the worktree (branch kept) and frees the port.
- `growth run --jobs N`: the machine runner takes machine jobs (build, link graph, gate, shots, click-test, own-copy,
  READY) side by side, under the browser pool and a load guard. Project-specific commands (a project's own evidence
  and copy checks) are named in `growth.json` `machine_jobs`.

## 8. What does not change

The rules, the gate's checks and verdicts, the golden rule, the owner's yes, the signed approvals, the hooks'
behaviour. A page is READY under 3.0 exactly when it would be under 2.8.5.

## 9. How it is tested

- The full kit suite stays green; new tests for the store (parallel writers: 8 processes x 200 writes, no lost or
  repeated ids), mirrors (round trip byte for byte on the demo project; an outside edit is imported), the board
  (claim, lease expiry, needs, one claimer per job under 8 parallel claimers), the pacer (no two turns closer than 20 s),
  the shared-code lock (re-check only changed pages), the manifest (every tool in one kit), and "no direct mirror reads".
- Then on a copy of a real project: migrate, compare the mirrors with the originals, `growth doctor` gives the same
  answers, the 12 batch-2 pages go on the board at their real stages, two lanes open at once on their own ports, the
  runner checks pages side by side, the research pacer holds the 20 s gap. Then on the real project.

## 10. Build order

1. Store and the one access layer (core), with mirrors and migration of every direct reader.
2. Board, jobs, resources and the pacer; the manifest and its test (in parallel with 1, on the store's connection).
3. Lanes and the machine runner (after 2's interface is fixed).
4. Book: 01-flow and 04-lanes rewritten for the board; CHANGELOG; version 3.0.0.
5. Independent review on a different model; then the test on a real project.
